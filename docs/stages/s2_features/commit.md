# 2.2 Commit history (`commit.py`)

**Command:** `python -m skillsig features --only commit` · **Tests:** `tests/s2_features/test_commit.py` · [Back to s2](README.md)

## What it does

Turns the dataset's commit columns into authorship evidence. The dataset keeps only the **first and last** commit of each file (author, author type, message, date) plus a commit count, and only for 458,137 distinct skills (24.4%).

## How it works

All columns are computed in one DuckDB query over the representative rows, with Python functions registered as DuckDB functions so tests and the full run use the same code.

**AI trailer detector** (`ai_tools_in_message`). Finds `Co-authored-by:` lines (any case, anywhere in the message) and matches the value:

| Pattern | Tool |
|---|---|
| `claude` or `anthropic` | claude |
| `cursor` | cursor |
| `copilot` | copilot |
| `codex` or `openai` | codex |
| `gemini` | gemini |

A tool named only in the subject or body ("add claude skill") does not count.

**Extended detector** (`ai_tools_in_message_ext`, task T35). A superset that also counts:

- other agents on a `Co-authored-by` line: `devin`, `aider`, `windsurf`, `cline`, `kiro`, `opencode`, `factory-droid`, `droid`, `junie`, `kimi`, `qwen`, `augment agent`, `google-labs-jules`; `jules` and `amp` only in their `[bot]` form, so a person's name never matches;
- footers such as `Generated with [Claude Code](…)`, `Generated by Copilot`, `Generated-by: Cursor`.

Code-review bots (`coderabbit`, `sourcery`, `codecov`, `deepsource`) are skipped: they co-author commits but do not write the skill.

**Author class** of the first commit:

| Class | Rule |
|---|---|
| `coding_agent_bot` | GitHub type `Bot` (or a `[bot]` login) whose login names `claude`, `cursor`, `copilot`, `codex`, `devin`, `jules` or `gemini`, and is not a release/sync bot |
| `noncoding_bot` | Any other bot, including logins with `github-actions`, `dependabot`, `release`, `sync`, `publish` |
| `user`, `organization` | GitHub account types |
| `unknown` | No type recorded |

**Batch size.** The number of distinct skills with history that the same repository added in the same first commit (`GROUP BY repo_full_name, first_commit_at`). `is_bulk = batch_size ≥ 6` (`thresholds.bulk_batch_min`).

**Message class** of the first commit, first match after removing trailer lines:

| Class | Matches |
|---|---|
| `install_sync_import` | install, sync, resync, import, vendor, materialise |
| `scaffold` | initial commit, first commit, init, initial drop |
| `conventional` | `feat:`, `fix:`, `chore:`, `docs:`, … |
| `add_upload` | add / added / create …, or "via upload" |
| `short_generic` | 12 characters or fewer |
| `other` | everything else, including a missing message |

Every column is `NULL` for a skill without history.

## Design decisions

- **Why only `Co-authored-by` lines?** A subject like "add claude skill" describes the topic, not the author. The trailer is the tool's own disclosure mechanism. The extended detector widens the tool list and adds footers, but keeps the rule that the tool must be named in a disclosure line.
- **Why keep both detectors?** v1 and v2 reproduce the Sprint 1 definition; v2.1 uses the extended one with its own reason codes, so the effect of the extension can be measured (4.6 asks a person to check 50 commit messages the extended detector flagged).
- **Why first and last commit?** That is all the dataset stores. 4.1 measures how much disclosure this misses (8% overall, 17% for skills with 3+ commits).
- **Why separate coding-agent bots from other bots?** `github-actions[bot]` committing a synced file says nothing about who wrote it; `copilot-swe-agent[bot]` does.
- **Why batch size, and why 6?** Installing a skill pack commits many skills at once. An AI trailer on that commit says the agent ran `git add`, not that it wrote 40 skills. Batches of 6 or more are treated as installs; 4.4 varies the threshold to 4 and 8.
- **Why is a missing value `NULL`, never `false`?** "No trailer seen" and "no history to look at" are different facts; the label rules must tell them apart ([stages README § 10](../README.md#10-insufficient-evidence-is-a-real-answer)).

## Full data vs dev sample

Dev mode keeps the sampled ids, but **batch size is still computed over the whole population**. A batch is a property of the repository's commit; counting it inside the sample would shrink every batch. Each skill's values are the same as in a full run.

## Tests (17)

- Claude co-author detected; a tool in the subject only, or outside a `Co-authored-by` line, does not count; a missing message gives no tools.
- Extended detector: positive and negative cases, it is a superset, and it leaves the original detector's result unchanged.
- Trailer stripping, message classes, author classes (parametrised cases).
- A run computes batch sizes, gives NULLs without history, and skips when unchanged; dev mode keeps full-population batch sizes; missing inputs name their commands.

## Limits

- Substring matching: a person named "Cursor…" or an `@openai.com` address counts as AI.
- Tools that never add a trailer (most Cursor and Copilot use) are invisible.
- Middle commits are invisible (see 4.1).
